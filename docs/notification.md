# Уведомления пользователю

`tnt-notification` — уведомления пользователю приложения: «вам
ответили», «подтвердите почту», «задание выполнено». Адресат — запись
модели, уведомление — объявленный вид с видом для каждого канала, каналы —
ящик на узле с отметкой «прочитано», письмо и вебхук. Всё, кроме ящика,
уходит очередью с повторами, а ящик и сообщения очереди пишутся одной
транзакцией `box`.

```lua
local notification = require('tnt.notification')
local queue = require('tnt.queue')

local notices = notification.new({
    inbox = notification.inbox(),
    channels = { mail = notification.mail({ mailer = require('tnt.mail'), views = views }) },
    queue = queue.declare('deliveries', { ttr = 30 }),
})

notices:declare('replied', {
    via = { 'inbox', 'mail' },
    inbox = function(data)
        return { title = 'Вам ответили', thread = data.thread }
    end,
    mail = function(data, user)
        return { subject = 'Вам ответили', view = 'mail.replied', data = { name = user.name, thread = data.thread } }
    end,
})

local users = notices:recipient(User, { addresses = { mail = 'email' } })

local report, err = users:notify(user, 'replied', { thread = 7 })
```

Зависимости: [`tnt-must`](https://github.com/tnt-skein/tnt-must)
(проверки аргументов), [`tnt-storage`](https://github.com/tnt-skein/tnt-storage)
(отказ `TntStorageFailure`), [`tnt-id`](https://github.com/tnt-skein/tnt-id)
(ULID уведомления), [`tnt-clock`](https://github.com/tnt-skein/tnt-clock)
(стенные часы отправки и прочтения),
[`tnt-hash`](https://github.com/tnt-skein/tnt-hash) (подпись вебхука)
и [`tnt-external`](https://github.com/tnt-skein/tnt-external) (подмена
часов и опознавателя в проверках). Очередь, почта, шаблоны и клиент HTTP
приходят аргументами: пакет знает их договор, а не их самих. Договор
выполняют [`tnt-queue`](https://github.com/tnt-skein/tnt-queue),
[`tnt-mail`](https://github.com/tnt-skein/tnt-mail),
[`tnt-template`](https://github.com/tnt-skein/tnt-template)
и [`tnt-http`](https://github.com/tnt-skein/tnt-http).

## Зачем пакет

Сказать что-то пользователю приложения — это четыре разные заботы, и
каждая, сделанная по месту, ломается по-своему:

- **Кому.** Адрес письма лежит в записи пользователя, адрес вебхука —
  в другой, а в ящике пользователь ищется по опознавателю из сессии.
  Опознаватель числом и строкой — два разных адресата, и уведомления
  одного человека расходятся по двум ящикам.
- **Что именно.** В ящике — короткая строка и ссылка, в письме — тема
  и тело по шаблону, вебхуку — данные JSON. Написанные в трёх обработчиках,
  три вида одного уведомления разъезжаются молча.
- **Как доставить.** Почтовик отвечает «попробуйте позже», вебхук — 503.
  Без очереди письмо теряется с первым отказом, а ожидание почтовика
  держит обработчик запроса.
- **Что с этим сделал человек.** Непрочитанное, пометка одного и всего,
  страница новых первыми — поверх спейса, который не выбирает
  непрочитанное всем обходом.

Пакет делает для этого пять вещей:

- **Адресат — род на модель.** `notices:recipient(User, …)` объявляет,
  как запись становится адресатом: род — имя спейса модели, адресат —
  опознаватель записи строкой, адрес канала — поле записи либо функция.
- **Вид уведомления — одно объявление.** Каналы (`via`) и вид для каждого
  канала объявляются вместе; канал без вида и вид без канала —
  исключение при объявлении, а не молчаливый пропуск.
- **Одна транзакция на всё.** Ящик и сообщения очереди для остальных
  каналов пишутся одной транзакцией `box`: уведомление легло целиком
  либо не легло вовсе. Внутри чужой транзакции оно становится её частью.
- **Доставка — очередью.** Письмо и вебхук уходят сообщением очереди
  с методом `send` — например, `tnt-queue`, — и повторяются ею с отступом;
  отказ канала несёт `retriable`, и то, что не пройдёт никогда
  (почтовик ответил 550, вебхук — 404), зарывается сразу.
- **Ящик на узле.** Спейс с признаком «прочитано» и двумя индексами
  поверх первичного: страница новых первыми с курсором, счёт
  непрочитанных по индексу, пометка одного — только своего — и всего
  кусками.

## Как пользоваться

### Ящик и шаг миграции

Спейс ящика заводит шаг миграции — функция от `box`, которую принимает
[`tnt-schema`](https://github.com/tnt-skein/tnt-schema), а без него —
любой, кто зовёт её с `box` при подъёме узла:

```lua
local schema = require('tnt.schema')

schema.register(12, notification.migration())                        -- спейс notifications
schema.register(13, notification.migration({ space = 'user_notices' }))
```

Шаг повторно безопасен: спейс и индексы, которые уже есть, не трогаются,
а недостающие заводятся.

| Поле кортежа | Что |
|---|---|
| `id` | ULID уведомления: время в старших знаках, порядок по нему — порядок по времени |
| `recipient_type` | род адресата — имя спейса модели |
| `recipient_id` | опознаватель адресата строкой |
| `kind` | вид уведомления |
| `data` | что отдал вид ящика |
| `created` | стенное время отправки, секунды |
| `read` | прочитано ли |
| `read_at` | когда прочитано; у непрочитанного нет |

Индексы: `primary` по `id`, `recipient` — `recipient_type, recipient_id,
id`, `unread` — `recipient_type, recipient_id, read, id`. Выборка
непрочитанных — ключ `{ род, адресат, false }` индекса `unread`, и ни
страница, ни счёт по нему прочитанного не обходят.

`notification.inbox({ space = 'user_notices' })` — ящик над спейсом;
по умолчанию `notifications`. Спейс спрашивается при каждом обращении:
ящик объявляют при загрузке модуля, а шаг миграции идёт позже. Спейса
нет — исключение без места: «ящик уведомлений: спейса notifications
нет — нужен шаг миграции notification.migration()».

### Центр: `new`

```lua
local notices = notification.new({
    inbox = notification.inbox(),
    channels = {
        mail = notification.mail({ mailer = require('tnt.mail'), views = views }),
        webhook = notification.webhook({ client = client, secret = secret }),
    },
    queue = queue.declare('deliveries', { ttr = 30 }),
})
```

| Ключ | Что |
|---|---|
| `inbox` | ящик на узле; без него канала `inbox` нет, и читать нечего |
| `channels` | каналы по имени: у канала есть `prepare` и `deliver` (ниже, «Свой канал»); имя `inbox` занято ящиком |
| `queue` | очередь с методом `send(body)`: без неё канал, кроме ящика, объявить нельзя |

Незнакомый ключ, канал без `prepare` или `deliver`, очередь без `send` —
исключение на строке вызывающего.

Очередь зовут не так, как спейс ящика: труба `tnt-queue` — спейс с именем
очереди, и `queue.declare('notifications')` рядом с ящиком по умолчанию
откажет — спейс `notifications` уже занят ящиком, и индекса трубы
в нём нет.

### Вид уведомления: `declare`

```lua
notices:declare('replied', {
    via = { 'inbox', 'mail' },
    inbox = function(data, user)
        return { title = 'Вам ответили', thread = data.thread }
    end,
    mail = function(data, user)
        return { subject = 'Вам ответили', view = 'mail.replied', data = { name = user.name } }
    end,
})
```

`via` — список каналов либо функция `(record, data) → список`: так вид
слушается настроек адресата.

```lua
notices:declare('digest', {
    via = function(user)
        return user.wants_mail and { 'inbox', 'mail' } or { 'inbox' }
    end,
    inbox = inbox_view,
    mail = mail_view,
})
```

Остальные ключи — виды каналов: функция `(data, record)`, которая отдаёт
то, из чего канал соберёт доставку. Исполняются они в файбере того, кто
отправляет, до транзакции.

Ошибка в объявлении — исключение на строке вызывающего:

| Что сделано не так | Текст броска |
|---|---|
| вид объявлен второй раз | `вид уведомления replied уже объявлен` |
| вид канала, которого нет | `вид уведомления greeted: канала mail у центра нет; есть inbox, push` |
| канал в `via` без вида | `вид уведомления greeted: канал push в via, а вида для него нет` |
| канал, а очереди у центра нет | `вид уведомления greeted: канал push ходит очередью, а queue центру не дали` |
| `via` не список и не функция | `вид уведомления greeted.via — массив или функция или вызываемая таблица, а не nil` |
| вид — не функция | `вид уведомления greeted.inbox — функция или вызываемая таблица, а не строка` |

Список из функции `via` сверяется так же, но при отправке: `вид
уведомления chosen.via — массив, а не строка`.

### Адресат: `recipient`

```lua
local users = notices:recipient(User, {
    key = 'id',                                     -- поле опознавателя; по умолчанию id
    addresses = {
        mail = 'email',                             -- поле записи
        webhook = function(user)                    -- либо функция от записи
            return user.hook_url
        end,
    },
})
```

Модель — модель `tnt-model` либо любая таблица с полем `space`: род
адресата — имя спейса. Адрес канала, которого у центра нет, —
исключение: «настройки адресата.addresses: канала mail у центра нет».

Опознаватель записи идёт строкой: строка как есть, целое число Lua —
только меньше 2^53, cdata `int64_t` и `uint64_t` — цифрами без `LL`.
Иначе — исключение: «адресат.id — непустая строка, целое меньше 2^53
либо cdata int64_t и uint64_t, а не 0.5». Число от 2^53 уже потеряло
цифры, и два пользователя сошлись бы в одного; большое целое модель
отдаёт cdata.

### Отправка: `notify`

`recipient:notify(record, kind, data) → report | nil, err`.

```lua
local report, err = users:notify(user, 'replied', { thread = 7 })
--> {
-->     id = '01K5…',                  -- ULID: один на все каналы
-->     stored = { 'inbox' },          -- легло в ящик
-->     queued = { 'mail' },           -- ушло в очередь
-->     skipped = {},                  -- у адресата нет адреса канала
--> }
```

Порядок работы:

1. виды каналов из `via` исполняются, и каналы готовят доставку: письмо
   собирается по шаблону, тело вебхука — строкой JSON;
2. канал, для которого у адресата нет адреса, пропускается и попадает
   в `skipped`: пользователь без почты получает уведомление в ящик,
   а не отказ;
3. строка ящика и сообщения очереди пишутся одной транзакцией.

Сообщение очереди — простые данные: `{ id, kind, created, recipient,
channel, payload }`, где `payload` — то, что приготовил канал.
`tnt-queue` берёт его как есть.

### Транзакции

Вне транзакции отправка открывает свою: ящик и сообщения очереди
фиксируются вместе, а отказ любого из них откатывает всё.

Внутри чужой транзакции отправка — её часть: «сохранили ответ
и уведомили» фиксируются одной транзакцией, и откат вызывающего уносит
уведомление.

```lua
box.begin()
box.space.replies:insert({ reply_id, thread, text })
users:notify(author, 'replied', { thread = thread })
box.commit()                                        -- ответ и уведомление — одной фиксацией
```

Отказ отправки внутри чужой транзакции откатывает только своё — до точки
сохранения, — и транзакция вызывающего остаётся ему открытой. Исключение
из работы (очередь бросила на негодном теле) уходит наверх как есть,
тоже после отката своего.

Чтобы сообщение очереди стало частью транзакции, отправка очереди
обязана быть транзакционной, как у `tnt-queue`. Канал по сети прямо
из транзакции не позвать: уступка оборвала бы её, а письмо, ушедшее
до отката, не вернуть, — поэтому канал без очереди отвергнут при
объявлении вида.

### Доставка: `handler`

```lua
local consumer = queue:consume(notices:handler(), { workers = 2 })
```

`notices:handler()` — обработчик для `queue:consume`: берёт канал
по имени из сообщения и отдаёт ему доставку. Итог — по договору
обработчика очереди (у `tnt-queue` — раздел
[«Итог обработчика»](https://github.com/tnt-skein/tnt-queue/blob/main/docs/queue.md#итог-обработчика)
её документа): значение подтверждает, пара `nil, err` возвращает
сообщение с отсрочкой, `err.retriable == false` зарывает сразу.
Негодное сообщение и канал, которого у центра больше нет, — отказ
`rejected` с `retriable = false`: вход из очереди недоверенный, а канал,
убранный из настроек, от повтора не вернётся.

`notices:handle(message)` — то же без обёртки: так доставку зовут
в проверках.

### Канал `inbox`: ящик на узле

Вид ящика отдаёт таблицу, и она ложится полем `data` как есть. Строка
кладётся в файбере вызывающего, мимо очереди: запись в свой спейс
не ходит по сети, и «уведомление появилось» видно сразу после `notify`.

```lua
local page = users:page(user, { unread = true, limit = 20 })
--> {
-->     items = {
-->         { id = '01K5…', kind = 'replied', data = { title = 'Вам ответили', thread = 7 },
-->           created = 1790000000.25, read = false },
-->     },
-->     next = '01K5…',               -- есть, если за страницей есть ещё
--> }

users:page(user, { after = page.next })             -- следующая страница
users:unread(user)                                  --> 3
users:mark_read(user, '01K5…')                      --> true
users:mark_all_read(user)                           --> 2
```

Читать можно и по записи, и по одному опознавателю: `users:page(7)`,
`users:unread('7')` — обработчику запроса хватает опознавателя
из личности.

| Вызов | Что | Итог |
|---|---|---|
| `page(target, opts)` | страница новых первыми | `{ items, next }` |
| `unread(target)` | сколько непрочитанных | число |
| `mark_read(target, id)` | пометить одно | `true`; чужое, прочитанное, несуществующее — `false`; отказ — `nil, err` |
| `mark_all_read(target)` | пометить всё | сколько помечено либо `nil, err` |

Настройки страницы:

| Ключ | Что | Умолчание |
|---|---|---|
| `limit` | сколько на странице, от 1 до 100 | 20 |
| `after` | курсор: `next` прежней страницы | нет |
| `unread` | только непрочитанные | `false` |

- **Курсор — опознаватель последнего уведомления страницы**, продолжение —
  обратный обход строго меньше него. Уведомления, пришедшие во время
  листания, на следующих страницах не появятся и порядок не собьют:
  они новее курсора. `next` нет у последней страницы.
- **Чужое не помечается и не видно.** По опознавателю из адресной строки
  нельзя ни пометить чужое уведомление, ни узнать, что оно есть: и то,
  и другое — `false`. Отметка прочтения остаётся первой.
- **Всё — кусками.** `mark_all_read` помечает по 500 непрочитанных
  одной транзакцией и уступает между кусками; внутри чужой транзакции
  куски — её часть и идут без уступок.

Страница и счёт идут и на узле для чтения; запись и пометка там
отказывают `unreachable`.

### Канал `mail`: письмо

```lua
local template = require('tnt.template')

local mail = notification.mail({
    mailer = require('tnt.mail'),                        -- send(letter) → true | false, err
    views = template.new({ path = 'resources/views' }),  -- render(name, data)
    from = 'noreply@example.org',                        -- отправитель поверх настроек почты
})
```

Вид письма отдаёт тему и тело — готовые либо именами шаблонов:

| Ключ | Что |
|---|---|
| `subject` | тема; обязательна |
| `text`, `html` | тело как есть |
| `view`, `text_view` | шаблоны тела с разметкой и простого текста — рисует `views` |
| `data` | данные шаблонов |

```lua
mail = function(data, user)
    return { subject = 'Вам ответили', view = 'mail.replied', data = { name = user.name, thread = data.thread } }
end
```

```html
{{-- resources/views/mail/replied.thtml.lua --}}
<p>{{ name }}, вам ответили в теме {{ thread }}</p>
```

Письмо собирается при отправке уведомления, и в очередь уходит готовым:
ошибка в шаблоне падает у того, кто отправлял, а не зарытым сообщением
через час. У письма — заголовок `X-Notification-Id` с опознавателем
уведомления. Нет адреса у адресата — письма нет: канал в `skipped`.

Негодное письмо — исключение с именем вида:

```
уведомление replied: письмо.subject — строка, а не nil
уведомление replied: у письма нет тела — дайте text, html, view либо text_view
уведомление replied: письмо по шаблону mail.replied, а views каналу писем не дали
```

Отказ почты — строка, и код SMTP в ней решает повтор: «сервер ответил
5xx» — адреса нет либо отказано навсегда, отказ `rejected`
с `retriable = false`, и сообщение зарывается сразу; прочее — сервер
занят, сеть, — `broken` с `retriable = true`, и очередь повторит.

### Канал `webhook`: запрос к службе

```lua
local http = require('tnt.http')

local webhook = notification.webhook({
    client = http.new({ timeout = 5 }),   -- post(url, opts), как у tnt-http
    url = 'https://push.example.org',     -- общий адрес: адресату без своего
    secret = 'тайна',                     -- подпись тела HMAC-SHA256
    headers = { authorization = 'Bearer …' },
})
```

Вид вебхука отдаёт таблицу — поле `data` тела. Тело — JSON:

```json
{"id": "01K5…", "kind": "replied", "created": 1790000000.25,
 "recipient": {"type": "users", "id": "7"}, "data": {"thread": 7}}
```

Запрос — `POST` с `content-type: application/json`,
`x-notification-id` и, с `secret`, `x-notification-signature:
sha256=<hex>` — HMAC-SHA256 тела. Получатель сверяет подпись тела как
есть, до разбора JSON, и отсекает повтор по `id`: доставка — «хотя бы
раз». Тайна в очередь не попадает: подпись считается перед самой
отправкой.

Повторов у запроса нет — `retry = { attempts = 1 }` на каждом вызове:
повторяет очередь, и два цикла повторов друг в друге множили бы
попытки. Род отказа — по коду ответа, как у драйверов поверх HTTP:

| Ответ | Род | Повтор |
|---|---|---|
| 2xx | — | доставлено |
| 429, 503 | `busy` | да |
| прочие 5xx | `broken` | да |
| прочие 4xx, 1xx, 3xx | `rejected`, `denied`, `conflict` | нет — зарыть |
| сеть, срок | `unreachable`, `timeout` | да |

Адрес, взятый у адресата, приходит от пользователя. Пакет не судит,
куда можно ходить узлу: запрет внутренних адресов — дело приложения,
которое этот адрес принимает.

### Свой канал

Канал — таблица с двумя методами:

```lua
local sms = {
    -- при отправке, в файбере вызывающего: итог — простые данные для очереди;
    -- nil — адресату этот канал не нужен, он попадёт в skipped
    prepare = function(self, content, address, notice)
        if address == nil then
            return nil
        end

        return { phone = address, text = content.text, id = notice.id }
    end,

    -- в работнике очереди: true либо nil, err с retriable
    deliver = function(self, payload, notice)
        return gateway:send(payload.phone, payload.text)
    end,
}

local notices = notification.new({ channels = { sms = sms }, queue = queue })
```

`notice` — `{ id, kind, created, recipient = { type, id } }`: опознаватель
один на все каналы уведомления.

### Отказ

Отказ — пара `nil, err`, где `err` — `TntStorageFailure`:

| Род | Когда | `retriable` |
|---|---|---|
| `unreachable` | узел только для чтения; очередь не принимает | `true` |
| `broken` | исключение `box` при записи ящика | `true`: своя транзакция откачена |
| `conflict` | фиксация не прошла: кворум синхронной репликации | `false` |
| что отдала очередь | отказ `send` — как есть | как у очереди |

```lua
local report, err = users:notify(user, 'replied', { thread = 7 })

err.kind                              --> 'unreachable'
tostring(err)                         --> 'ящик уведомлений не принимает: узел только для чтения'
```

Исключение — ошибка программиста: незнакомый вид, негодное объявление,
вид канала, вернувший не то, негодный опознаватель адресата, негодные
настройки страницы, пропущенный шаг миграции.

| Что сделано не так | Текст броска |
|---|---|
| `users:notify(user, 'greeted')` | `вида уведомления greeted нет; есть chosen, replied` |
| `users:notify(7, 'replied')` | `адресат — таблица, а не число` |
| вид ящика вернул строку | `вид уведомления replied.inbox вернул — таблица, а не строка` |
| `users:page(7, { limit = 101 })` | `настройки страницы.limit — число от 1 до 100, а не 101` |
| чтение у центра без ящика | `уведомления без ящика: inbox центру не дали, и читать нечего` |

Бросок проверки аргумента начинается с места вызывающего
(`app/replies.lua:12: …`); отказ о письме и теле вебхука называет вид
уведомления и идёт без места — строку, которую надо чинить, называет вид.

### Подмена в проверках

| Модуль | Имена |
|---|---|
| `tnt.notification.center` | `ulid` — опознаватель уведомления, `now` — стенные часы отправки |
| `tnt.notification.inbox` | `now` — стенные часы прочтения |

```lua
local center = require('tnt.notification.center')

center._set_source({ ulid = function() return 'n-01' end })
-- …
center._set_source(nil)                   -- настоящие средства вернулись
```

## Чем пришлось поступиться

- **Каналы, кроме ящика, — только очередью.** Письма «прямо сейчас,
  без очереди» нет: канал по сети в транзакции уведомления оборвал бы её.
  В проверках доставку зовут `notices:handle(message)` напрямую.
- **Доставка — «хотя бы раз».** Письмо и вебхук могут уйти дважды:
  обработчик дольше `ttr`, обрыв между отправкой и подтверждением.
  Вебхук отсекает повтор по `id`, у письма — заголовок
  `X-Notification-Id`.
- **Повтор `notify` — новое уведомление.** Опознаватель рождается
  на каждом вызове: отправка, повторённая вызывающим после отказа
  фиксации, не удвоит ничего, но повторённая после удачи — удвоит.
- **Письмо собирается при отправке.** В очереди лежит готовое письмо:
  правка шаблона не меняет уже поставленных писем, а данные записи —
  те, что были в миг отправки.
- **Ящик живёт на узле, где идёт отправка.** Спейс ящика — обычный
  спейс узла: в репликасете его видят реплики, а в шардированном кластере
  отправку зовут там, где лежит спейс, — на хранилище. Ящика моделью
  `tnt-model`, который жил бы в любой топологии, пока нет.
- **Уборки старого нет.** Прочитанное лежит, пока приложение его
  не удалит: срок хранения — решение приложения, а не пакета.
- **`read_at` и `created` — стенные часы.** Перевод часов назад даёт
  отметку прочтения раньше отправки; порядок ящика от этого не страдает —
  он идёт по ULID.
- **Отказ почты читается по тексту.** Код SMTP берётся из строки
  «сервер ответил 5xx», которую отдаёт `tnt-mail`: у почты отказ —
  строка, а не таблица с кодом.
- **Адрес вебхука не проверяется.** Куда можно ходить узлу, решает
  приложение: адрес пользователя вида `http://127.0.0.1:…` пакет
  отправит.

## Проверки

Проверки лежат в `test/` и идут на luatest: `.rocks/bin/luatest test/`.
Модули пакета берутся из исходников, зависимости — установленными.
Очередь и шаблоны пакету приходят аргументами, а проверкам нужны
настоящие: `make deps` ставит `tnt-queue` и `tnt-template` рядом
с зависимостями.

В процессе проверок — чистые части: настройки центра и ящика, объявление видов
и его отказы, род адресата и опознаватель строкой (строка, число, границы
2^53, cdata), адрес канала полем и функцией, отказы аргументов с местом
вызывающего, обработчик очереди на двойнике канала, канал писем
на двойниках почты и шаблонов (тело готовое и по шаблону, адреса нет,
негодное письмо, 5xx и 4xx), канал вебхука на двойнике клиента (тело,
общий адрес, заголовки и подпись, род отказа по коду ответа и сети).

Две группы поднимают узел. Первая — ящик и транзакция на настоящем
`box`: шаг миграции и его повтор, уведомление в ящике и в очереди,
пропуск канала без адреса, пометка своего и чужого, пометка всего
кусками вне транзакции и внутри неё, страница с курсором и границы
соседей по индексу, откат вызывающего, отказ очереди вне транзакции
и внутри неё до точки сохранения, исключение очереди, узел для чтения,
отказ `box` при записи, фиксация без кворума синхронной репликации,
пропущенный шаг миграции. Вторая — настоящая очередь `tnt-queue`
и шаблоны `tnt-template`: письмо по шаблону, поставленное до перезапуска
узла, уходит работником после него, а ящик переживает перезапуск; отказ
4xx почты повторяется, 550 — зарывается с первой попытки; откат
вызывающего оставляет очередь пустой.

Покрытие строк — 100 %, убитых мутантов — 100 % (55 проверок, 18 из них —
на узлах; 334 мутанта в пяти модулях). Примеры этого документа прогнаны
на Tarantool 3.8 с настоящими `tnt-queue` и `tnt-template`, вебхук —
против живого сервера HTTP.
